## 10. The migration-4 experiment — what was actually run

`sqlite3 3.45.1` via the Python standard library, against the real migration-1 table shapes with
Arabic product names and three historical lines. Scripts kept in `docs/evidence/`:

```
migration4-rebuild-experiment.py          T1 crash rollback · T2 commit + history fingerprint
migration4-constraints-experiment.py      T3 bounded check · T4 whole-unit exactness · T5 guards · T7 DROP vs triggers
migration4-ordering-and-ties-experiment.py  T6 ordering (corrected) · T8 the tie case · T9 overflow headroom
```

**Caveat on the instrument, stated because it matters.** The app links its own SQLite through
`better-sqlite3 ^13`; this experiment used Python's, version 3.45.1. The behaviours exercised —
transactional DDL, `ALTER TABLE … RENAME`, CHECK with `abs()`, trigger timing, foreign-key
enforcement — are long-standing and stable across these versions, but **the experiment is evidence
about SQLite, not about the shipped binary.** The step that closes that gap is the v3 → v4 upgrade
test in §18, which runs through the app's own `openDatabase`. Until that test exists, Option B is
**proven at the SQLite level and unproven at the build level.**

A second limitation, found the hard way: Python's `executescript()` issues an implicit `COMMIT`, so
the first attempt silently tested the rebuild **outside** a transaction — exactly the property under
examination. It was re-run statement by statement, and only then did T1 mean anything.

## 17. 🔴 The test environment, measured — and what it means for the numbers

The database-backed tests **cannot run on this machine**, and the reason is not the code:

```
better-sqlite3@13  engines  ->  { "node": ">=22" }
this machine                ->  node v20.20.2
CI (.github/workflows)      ->  node-version: 22
the repo itself             ->  no "engines" field, no .nvmrc
```

The shipped `linux-x64` prebuild **loads** under Node 20 and then **segfaults on the first query** —
so a developer on Node 20 gets a core dump, not a message. `npm rebuild --build-from-source`
reported success but produced no `build/Release/*.node`; `nvm install 22` exited 0 and installed
nothing (no network); Electron's bundled Node 22 is unreachable because the Electron binary was
never downloaded either.

**Consequence for the report, stated honestly:** 93 tests across the 11 files that need no native
driver all pass here, including the import test that had to be corrected. The 12 files that open
SQLite — 10 pre-existing and 2 new — are written and typechecked but **were not executed here**.
Windows CI runs them; that is where the claim will be closed.

**Recommendation (not done — it is outside the approved scope):** add `"engines": { "node": ">=22" }`
and an `.nvmrc` to this repository. Two lines that turn a segfault into a sentence.

## 31. 🔴 The cause, proven — not guessed

`tests/main/settingsStore.test.ts` seeded its fake file system with the literal string
`"/profile/settings.json"`, while `SettingsStore` builds its path with `path.join`:

```
join('/profile','settings.json')   on Windows  →  \profile\settings.json
the test's seeded Map key                      →  /profile/settings.json
                                   match?      →  NO   ⇒ exists() false, defaults reported
on POSIX the same join             →  /profile/settings.json   ⇒ matches, which is why it passed here
```

**Proven under Windows semantics on this Linux machine**, by mocking `node:path` to its `win32`
implementation and re-running the logic. Three assertions, all passing:

1. the store's path really is `\profile\settings.json`;
2. a file seeded at that path **is** found, and a language choice round-trips;
3. 🔴 the **old** hardcoded POSIX key is **not** found — reproducing the CI failure exactly.

The probe was temporary and is not committed; the permanent guard is in §32.

## 32. The fix, and the test that was asserting nothing
